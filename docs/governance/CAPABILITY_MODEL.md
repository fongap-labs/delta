# 能力模型

## 1. 能力原则

新增功能优先扩展，不分叉核心。

### ❌ 错误做法 / 反面教材

为单项能力复制运行时。

```text
新功能 → 第二套核心引擎
```

### ✅ 正确做法 / 规范范例

复用唯一能力合同。

```text
已有技能 → 新增执行器或连接器 → 必要时修改公开合同
```

## 2. 能力定义

每项能力必须声明身份及权限。

### ❌ 错误做法 / 反面教材

只有名称，没有执行边界。

```text
能力：文件处理
```

### ✅ 正确做法 / 规范范例

声明完整的公开属性。

```text
身份 + 用途 + 权限 + 依赖 + 执行模型 + 生命周期
```

## 3. 能力分类

按职责选择技能、执行器或连接器。

### ❌ 错误做法 / 反面教材

让知识型技能直接写入权威状态。

```text
技能 → 跳过授权 → 写入核心数据库
```

### ✅ 正确做法 / 规范范例

职责与执行边界分离。

```text
技能：知识与任务流程
执行器：受控文件处理和计算
连接器：受控外部数据访问
领域能力：专业工作流组合
```

能力均通过公开合同执行，不拥有独立系统权威。

## 4. 生命周期

未经验证及授权不得执行。

### ❌ 错误做法 / 反面教材

注册后直接获得全部权限。

```text
注册 → 任意执行
```

### ✅ 正确做法 / 规范范例

按统一流程运行。

```text
定义 → 注册 → 验证 → 授权 → 执行 → 报告
```

## 5. 权威边界

核心控制审批、调度和状态。

### ❌ 错误做法 / 反面教材

为能力另建独立审批和状态系统。

```text
能力核心 + 能力运行时 + 能力审批 + 能力状态
```

### ✅ 正确做法 / 规范范例

公开接口由核心统一监督。

```text
可选扩展 → 公开开发工具包与合同 → 基础运行时
                                     → 审批、调度、状态
```

核心提供通用基础能力，扩展提供高级及领域能力；不得把可选扩展变成第二套应用、运行时或持久化权威。
