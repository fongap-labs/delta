# 扩展边界

## 1. 依赖方向

基础产品不得依赖可选扩展。

### ❌ 错误做法 / 反面教材

从核心导入扩展实现。

```text
基础产品 → 可选扩展源码
可选扩展 → 基础产品私有实现
```

### ✅ 正确做法 / 规范范例

只按公开合同建立单向依赖。

```text
可选扩展 → 公开开发工具包、接口和合同 → 基础产品
```

基础产品未安装扩展时必须能构建、测试、启动和完成基本任务。

## 2. 权威归属

运行与审批权威只属于基础产品。

### ❌ 错误做法 / 反面教材

扩展单独持有核心状态。

```text
扩展 → 独立数据库 + 独立审批 + 独立执行引擎
```

### ✅ 正确做法 / 规范范例

通过公开能力宿主申请执行。

```text
基础产品：运行时、信任、权限、审批、状态、恢复、账本
扩展：技能、执行器、连接器、托管服务适配器、展示元数据
```

核心不得写入扩展专属实现或权益判断。

## 3. 安装隔离

每个扩展必须独立安装、移除和诊断。

### ❌ 错误做法 / 反面教材

扩展损坏导致基础产品无法启动。

```text
一个扩展加载失败 → 整个产品启动失败
```

### ✅ 正确做法 / 规范范例

按来源隔离扩展目录与清单。

```text
<delta-state>/extensions/<source>/
```

基础产品独立发现并校验清单；失败的扩展不得影响无关扩展。

## 4. 兼容与验证

公开合同变更必须经过版本审查。

### ❌ 错误做法 / 反面教材

直接依赖最新主分支或私有模块。

```text
扩展 → 内部代码 main → 直接发布
```

### ✅ 正确做法 / 规范范例

按版本化的公开合同检查。

```text
公开合同 → 兼容性测试 → 权限验证 → 安装冒烟 → 发布
```

架构边界由 `projects/delta/scripts/check_architecture_boundary.py` 校验；仓库边界由 `projects/delta/scripts/check_repository_boundary.py` 校验。二者必须在适用的持续集成和本地检查中执行。
