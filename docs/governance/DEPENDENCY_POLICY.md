# 依赖治理

## 1. 依赖边界

核心依赖与技能依赖必须隔离。

### ❌ 错误做法 / 反面教材

为一个工具向核心添加大型运行时。

```text
可选视频工具 → Rust 核心强制安装视频工具链
```

### ✅ 正确做法 / 规范范例

按实际能力所属范围管理依赖。

```text
核心：Rust / Tauri / TypeScript
扩展：Worker 专用工具、模型与媒体运行时
```

只有稳定的基础能力才能成为核心依赖；不因单一技能扩大核心安装体积。

## 2. 依赖升级

更新必须验证兼容、安全与性能。

### ❌ 错误做法 / 反面教材

直接合并主版本升级。

```text
发现新版本 → 自动合并
```

### ✅ 正确做法 / 规范范例

按风险评审并执行回归。

```text
漏洞与许可 → 接口变更 → 运行时和数值结果
           → 打包与性能 → 中央检查
```

补丁、小版本升级需通过适用检查；主版本升级必须核对迁移、公开接口及下游消费方。安全修复不得无故拖延。

## 3. 锁定与复现

依赖版本必须可复现。

### ❌ 错误做法 / 反面教材

手动修改锁文件绕过解析。

```text
编辑 package-lock.json → 跳过安装验证
```

### ✅ 正确做法 / 规范范例

使用包管理工具并在持续集成重现。

```bash
npm ci
cargo test
```

锁文件进入版本控制；工作流外部依赖固定到不可变提交。不得用忽略、跳过或宽泛版本号绕过缺陷。

## 4. 自动更新

依赖机器人不得绕开合并门禁。

### ❌ 错误做法 / 反面教材

自动更新直接写主分支。

```text
依赖机器人 → main
```

### ✅ 正确做法 / 规范范例

生成合并请求并完整验证。

```text
更新建议 → 合并请求 → 风险检查 → 中央门禁 → 合并
```

自动合并以仓库现行策略及必要审批为准。冲突更新分开评估，不批量绕过。

## 5. 安全与清理

不再使用的依赖必须删除。

### ❌ 错误做法 / 反面教材

保留退役的 Python 后端和重复工具链。

```text
新实现 + 已退役实现 + 重复构建依赖
```

### ✅ 正确做法 / 规范范例

替换完成时移除旧依赖与配置。

```text
新实现 → 迁移测试 → 删除旧依赖、脚本与锁定项
```

删除前核对发布资产、Worker 沙箱和旧会话恢复，不仅比较文件数量。
