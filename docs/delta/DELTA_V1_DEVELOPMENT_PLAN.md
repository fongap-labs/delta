# Delta 首版开发计划与实施指令

> 状态：开发计划，2026-11-23。本文描述目标和执行要求，不表示 Delta 首版已经实现、验收或发布。实施状态见 [文档与导入证据索引](README.md)。
>
> 项目目标：源于 Harness，不受限于 Harness；首次导入即完成裁剪并形成可运行产品，后续能够模块化演进，最终可独立发展。

## 一、首版交付目标

首版交付 Windows x64 便携版 Delta 桌面应用及经验证的精简 `delta` CLI。用户无需安装 Delta 即可从解压目录启动，并使用已批准的核心能力。发行根目录采用：

```text
Delta/
├── App/       应用和必要运行组件
├── Data/      Delta 管理的用户数据、配置和会话
└── Other/     必要的随包资料和支持文件
```

具体可执行文件和子目录以实际打包验证为准。Delta 管理的数据以便携根目录为基准，不能依赖当前工作目录；操作系统及外部软件产生的数据须核实并说明，不预先承诺绝对零系统痕迹。

### 首版必须保留的产品能力

1. 桌面、CLI、会话保存恢复、工作区、附件、上下文压缩。
2. 模型调用、流式交互、Agent、计划、工作流和子智能体。
3. 文件、终端、工具执行、权限确认及必要安全边界。
4. 插件安装与生命周期、MCP、Skills 和必要的插件协议兼容。
5. CUA、浏览器操作、Forge（GitHub / GitLab）、Worktree、LiveShare。按此前决定默认关闭或由用户主动启用；须逐项实际验证。LiveShare 首版使用用户自托管 HTTPS/WSS Relay，默认只读，链接限时且可撤销。
6. 第一方界面简体中文与英文：任何中文系统变体默认简体中文，其他语言默认英文；用户可手动覆盖。维护文档中文，许可及协议原文按要求保留。

语言补充要求：将**应用界面语言**与**会话回复语言**分开处理。会话窗口中的第一方按钮、状态、命令提示、审批确认、错误及无障碍文字随应用设置显示简体中文或英文，不因该会话的文字语言改变。机器协议、工具 schema、系统指令和供 Agent 阅读的操作说明使用英文。用户文本和外部内容保留原样。Agent 面向用户的自然语言回复遵从用户明确指定的语言；否则跟随用户当前自然语言表达并结合会话上下文保持连贯，混合语言或不确定时延续该会话最近明确使用的回复语言。切换应用界面语言不回译或改写已有会话内容。

DeepSeek 官方账号是可选能力：应尽力实现并验证；若官方登录因客户端身份、服务或条款限制不可用，记录并向用户明确说明，但不阻断首发。未登录时，用户应能通过支持的模型配置正常使用。此例外不自动适用于其他功能或 LiveShare。

### 必须排除

- Harness 的遥测、产品行为收集、反馈上传、非必要跟踪标识与相关默认入口；必要本地日志不得自动上传。
- 无关官网、官方发行设施、插件市场索引生成器、无关实验和其他不属于首版的资产；不能因此删除桌面必需前端或原生插件安装能力。
- Harness 处于实验状态的功能实现及其专属装配。**排除上游实验实现不等于排除同类产品功能**：五项能力须选择经核验的非实验实现或由 Delta 自行实现，不得通过重命名上游实验代码规避要求。

第三方插件、MCP、模型和用户主动启用的联网服务有独立权限及网络边界；默认本地优先，不默认云同步。插件管理不自动意味着插件沙箱。

## 三、架构及仓库原则

采用模块化单体：`Delta Desktop / CLI → Delta 产品与能力模块 → 具体实现`。Delta 掌握产品行为、数据和演进方向；首版对已验证的非实验上游实现适度复用。针对真实变化或替换需求才引入接口，不复制整套 Agent、会话或插件内核。

按能力明确智能体、模型、会话、工具与权限、插件、工作区、配置与语言、桌面和 CLI 的归属。五项新实现有各自的授权、生命周期、配置和测试边界。目录是实现细节：以固定 SHA 的工作区和依赖关系为依据，识别上游来源及 Delta 自有代码；不为目录整齐机械搬迁，也不把上游目录永久固化为 Delta 的架构约束。

Action-Worker 是中央治理与执行权威：跨仓库策略、权限、可信测试、合并和发布控制归中央。Delta 提供产品源码、构建声明和允许的项目专属配置；不复制一套独立治理或放宽门禁。共用规范引用 Action-Worker，产品文档只维护 Delta 专属架构与规则。

## 四、实施阶段

### 阶段 0：固定目标、来源和工作区

1. 读取 Delta、Action-Worker 和上游的当前仓库指令、机器策略、构建清单与相关规范；核对基线是否变化。
2. 确定并记录不可变上游 SHA、Delta 基线、中央治理版本、构建工具版本和许可证。
3. 建立彼此分离的上游输入区、仓库外处理区、证据区和 Delta 仓库。**完整、未经裁剪的 Harness 不得进入 Delta 仓库任何分支。**
4. 将上述能力转成可测试矩阵：输入输出、权限、依赖、配置、错误和验收。识别必须由产品决策的外部服务、许可或未明确的能力边界；不以猜测宣布已支持。

**完成条件：**来源和范围有记录；可识别技术与外部依赖；Delta 仓库未出现未经处理的上游源码。

### 阶段 1：模块和依赖盘点

1. 以 Desktop、Desktop Host、CLI、前端及已批准能力为入口，分析包依赖、Cordis Profile/Bundle 动态装配、原生组件、资源、生成物和安装脚本。
2. 形成保留、排除和待核查清单；标出被保留核心功能与上游实验代码的交集。静态依赖图不是最终白名单。
3. 区分 CLI 运行依赖与对外命令；保留必要的原生包身份和第三方协议，避免全局重命名。
4. 审查遥测、反馈、产品分析、匿名标识、网络出站、凭据、插件来源及生命周期脚本；区分合法模型调用和用户授权服务。
5. 记录 Delta 自有模块、上游保留实现、必要适配及本地补丁；每处改动写明目的、影响和验证。

**完成条件：**核心能力的依赖与动态入口可追溯；五项能力与实验实现的冲突清楚；未知依赖未被静默加入。

### 阶段 2：五项能力的非实验实现

先为每项明确首版最小行为与证据，再选择经核验的非实验第三方方案或 Delta 自有实现。第三方依赖不改变 Harness 作为产品源码唯一上游的定位；须核查许可、维护、安全、Windows x64、离线/联网及便携条件。

| 能力 | 首版验证任务 | 需要解决的关键问题 |
|---|---|---|
| CUA | 授权后观察并操作 Windows 窗口；验证拒绝与取消 | 可靠的非实验实现、辅助组件、权限及便携打包 |
| 浏览器操作 | 在用户启用后打开、读取并操作网页 | 浏览器和提供方来源、资源清理、用户数据与权限 |
| Forge | 使用 GitHub 和 GitLab 完成代表性的变更请求读取 | 两种服务的认证、必要工具、错误及权限 |
| Worktree | 创建、进入、退出独立工作目录 | Git 依赖、并发、目录隔离及未提交更改保护 |
| LiveShare | 创建分享、授权访问、撤销和服务失败处理 | 中继/服务来源、身份、部署、权限及外联 |

若方案需远程部署、付费服务或用户凭据，先完成无需这些条件的设计和实现，并准确记录外部前提；不得声称服务已存在或登录必然可用。不能将这五项擅自移出首版；缺少实现或真实验收时，首版保持未完成。

**完成条件：**五项各自有可追溯实现来源、依赖、可执行配置和真实测试方案；实际完成以阶段 5 验收为准。

### 阶段 3：中央治理准备

1. 通过 Action-Worker 的受信任变更路径，为新 Delta 适配测试包、产品执行清单、Windows x64 构建与验收环境、来源识别及必要测试归属。
2. 核对旧 Python 测试包及其基线迁移方式；不能通过删除测试、减少检查或扩大豁免制造绿灯。
3. 核对当前 Delta 基线与中央旧的固定 SHA 导入规则不匹配的问题，设计精准可审计的来源比较与回归测试，不能假设现有例外自动适用。
4. PR 不可信代码、依赖安装和构建任务在受限环境执行；中央凭据和发布权限不交给不可信任务。证据绑定不可变源码和策略版本。

**完成条件：**中央策略、执行器与测试经自身门禁验证，能对实际 Delta 候选执行；不会因业务 PR 自行修改规则而绕过检查。

### 阶段 4：在 Delta 仓库外完成候选源码

1. 根据固定 SHA、能力矩阵和依赖清单，生成完整的 Delta 候选；删除禁止能力及相关源码、入口、装配、依赖、构建资源和产物。
2. 完成五项能力的非实验来源或 Delta 自有实现，保留批准的 Harness 核心能力、插件和 CLI。
3. 完成 Delta 名称、图标、可执行入口、语言、数据隔离及便携目录。对 Electron `userData`、Host/CLI 的 `DSH_HOME`、子进程、日志、附件和临时文件逐项验证；不静默复用 Harness 凭据。
4. 完成中文文档与中英界面；检查 key、占位符、错误、CLI 和无障碍标签，保留第三方许可原文。
5. 更新工作区、锁文件、构建与发行配置；保留 MIT、Apache-2.0 及其他适用的第三方声明。固定或记录工具链、文件清单、裁剪规则、补丁及来源。
6. 执行仓库外预检：静态检查、依赖安装与构建、便携目录检查、真实运行和核心能力回归。失败后调整规则或补丁，重新生成或修复候选；所有修复必须可追溯且可重放。

**完成条件：**候选源码已完成全部批准的删减和 Delta 化；五项能力及核心功能预检通过；未裁剪上游源码未进入 Delta 仓库。预检不代替中央最终验收。

### 阶段 5：首次导入和最终验收

1. 仅将阶段 4 完成的候选源码首次导入 Delta 受控分支，检查导入前后文件清单及校验结果。
2. 对最终待合并 commit 执行中央检查与真实 Windows x64 便携包验收。
3. 测试 `App/Data/Other` 结构、复制到其他路径、空格与中文路径、只读目录、并发、退出重启及用户数据恢复；检查与同机 Harness、`dsh` 的隔离和共存。
4. 真实模型、工具、会话、插件、CLI、五项能力、权限、语言、网络行为和许可检查逐项记录；仅官方账号登录按已批准例外处理。
5. 未通过则在受控分支修复或返回仓库外处理区重新生成，修复同步回处理方案；重新运行受影响检查。全部通过、中央门禁允许后才合入 `main`。

**完成条件：**源码、产物、测试和证据绑定同一最终版本；未完成项不得标为通过。首次产品合入是完整成品，不是等待后续裁剪的上游快照。

### 阶段 6：持续同步与演进

比较上次实际采用的上游 SHA、新上游 SHA 和当前 Delta。审查上游变化、批准模块与依赖、排除遥测和上游实验实现、重放 Delta 改动、处理冲突、执行回归并生成候选 PR。记录已吸收、部分吸收、排除和延后及原因。同步失败保持上一稳定版本；安全修复可受控回植。演练旧版本升级、会话格式迁移、备份和回退。

## 六、可直接使用的实施指令

将以下内容交给负责实施的开发智能体。执行前以实际仓库的最新指令和机器策略为准，并按用户后续明确决定更新。

```text
你负责实施 fongap-labs/delta 首版。先阅读 Delta、Action-Worker 和固定版本 Harness 的相关仓库指令、机器策略、构建与依赖配置，然后继续执行，不要只输出计划。

目标：Delta 源于 Harness，但不受限于 Harness；首版首次导入即为完成裁剪和 Delta 化、可运行的产品。首发 Windows x64 便携版，发行根目录为 App、Data、Other，Delta 自有数据与同机 Harness 隔离。

必须保留已批准的 Harness 核心能力、插件/MCP/Skills、精简 delta CLI、CUA、浏览器操作、Forge（GitHub/GitLab）、Worktree、LiveShare。五项功能默认关闭或由用户主动启用；不直接吸收 Harness 处于实验状态的功能实现。分别选择经核验的非实验实现或开发 Delta 自有实现；不得通过重命名上游实验代码规避。任何功能未完成或未验收，不得宣称首版通过。

DeepSeek 官方账号可选，登录失败不阻断首发；不登录时支持用户配置的模型。此例外不适用于其他能力。默认本地优先，删除未经授权的遥测、反馈上报及非必要追踪；区分用户授权的模型、插件及服务联网。
```
