# ADR-0065：渐进授权阶梯

状态：**提议**（实现按所有者 2026-10-25 对路线图任务 A3 的批准进行；待所有者确认后改为"已接受"）。

## 背景

路线图 A3 要求：授权可以由单次逐级升到会话、再到工作区；升级必须由用户明确点击，界面可见，可以撤销；反复拒绝触发熔断（已实现，见 CHANGELOG）。明确不做"审查模型自动批准"。

撰写时的现状（已核对）：

1. 审批卡片有"允许一次""始终允许"（会话内，针对工具）与"始终允许此命令"。会话授权只存在于内存，用户看不到当前有哪些，也无法撤销。
2. 没有工作区一级的规则。
3. **缺陷**：运行时在 `needs_user` 为 false 的"硬拒绝"上也认会话授权。例如用户先前允许了某工具，随后会话切到 Plan 模式（Plan 模式拒绝一切修改），该工具仍会执行；同样，出站档位或副作用检查给出的拒绝也会被授权越过。授权回答的是"要不要问"，不能推翻"不允许"。

## 决定

### 1. 授权只回答问题，不推翻拒绝

只有在策略结果是"需要用户批准"（`needs_user` 为真）时，会话授权与工作区规则才生效。Plan 模式的拒绝、副作用与出站档位的拒绝照常拒绝。需要逐次批准的出站调用，仍然不受任何授权影响（ADR-0061）。

### 2. 三级阶梯

| 级别 | 按钮 | 保存位置 | 寿命 |
|---|---|---|---|
| 单次 | 允许一次 | 不保存 | 这一次调用 |
| 会话 | 本会话中允许 | 会话的审批控制器（内存） | 会话结束或被收回 |
| 工作区 | 在此工作区始终允许 | 状态目录 `workspace_rules.json`（仅所有者可读写，原子写入） | 直到被收回 |

- 工作区规则是"整个工具"，或者对执行命令的工具是"恰好这一条命令"；不做通配或前缀。每个工作区最多 200 条。
- 规则属于创建它的工作区（按规范化路径），对该工作区的所有会话与定时任务运行生效；其他工作区不受影响。没有工作区的会话不能创建规则，按钮不出现。
- 文件读不出来或格式不符时，没有任何规则生效（失败即关闭），并且不会被覆盖。
- 这一级不复用 `set_path_rule`：那是出站路径规则，只管内容能否发到外部；工作区规则管本机动作的免询问。

### 3. 哪些调用不能成为规则

出站调用、`web`、`mcp`、`connector` 类工具、副作用为 `external_write` 或 `destructive` 的工具，以及 `save_skill`。界面不出现按钮，运行时也会拒绝建规则：此次调用仍按"允许一次"执行，账本记录 `approval.rule_refused`。

### 4. 可见、可撤销

设置之外，会话右侧栏"权限"区列出当前免询问的全部项目，标明"本会话"或"此工作区"，每项一个"收回"按钮。收回后下一次匹配的调用重新询问。创建与收回工作区规则都写入审计日志（工具名 `approval.rule`）。

### 5. 不做

不引入"审查模型替用户批准"。不做规则的有效期、通配、导入导出；不做跨工作区的全局规则。

## 后果

- 新增 `workspace_rules` 模块、`ApprovalDecision::AlwaysWorkspace`、`ApprovalController::grants/revoke_grant`，以及 Tauri 命令 `approval_rules`、`revoke_approval_rule`。
- 审批卡片原来的"始终允许"改称"本会话中允许"，使两级不会混淆；新增"在此工作区始终允许"。
- 回归测试：Plan 模式下会话授权与工作区规则都不能放行修改；会话授权→收回→重新询问；工作区规则跨会话生效、跨工作区不生效、收回后重新询问；破坏性调用不能成为规则。

## 未验证事项

- Tauri 命令（`runtime_ipc.rs`、`lib.rs`）在本次开发环境无法编译，仅按同文件中同类命令对照写成；核心逻辑在 `delta-core` 中并有测试。
- 路线图验收中"private_only 档位下断路器不发网络请求"：断路器只写本地数据库和收件箱，代码里没有网络调用，没有为此单独加测试。
- 无人值守运行里，工作区规则同样生效；是否应当对定时任务更严格，需要所有者决定。
- 收件箱里停放的审批卡片（`InboxItemCard`）没有加"在此工作区始终允许"按钮；只有会话内的卡片有。
