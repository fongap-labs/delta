# ADR-0086：视觉桥接（Vision Bridge）

状态：**已接受**（所有者，2026-10-28，同意第一版范围：内置能力、自动触发、参数按模型可配置）。

## 背景

- 图片附件直接转成模型的图片块（`runtime.rs` 的 `provider_user_content`），运行时不区分模型能力。只支持文本的模型收到图片时没有任何处理。
- ModLens 证明“视觉模型先描述，文本模型接收描述”的做法可行。但它通过外部 CLI 调用第三方服务，不符合 Delta 的权威与出口边界（ADR-0078、ADR-0079、ADR-0057）。

## 决定

1. **能力内置于 Rust 核心。** 请求构造在 `crates/delta-core/src/vision.rs`，发送与记录在 `runtime/vision_turn.rs`。不引入外部 CLI 或第三方进程。
2. **视觉模型是用户指定的一个已配置模型**（`vision_model`），其凭据经 model authority 解析。它的请求与摘要请求一样经过出口门禁（`gate_model_request`），并使用本轮代理。
3. **能力判定。** `vision_support[model_id]` 标记模型是否自己能收图，默认视为不支持。只有同时满足“配置了视觉模型”与“目标模型未标记为支持图片”时才启用桥接。未配置视觉模型时保持原有行为，不改变现有用户的图片流程。
4. **自动触发。** 新的用户消息含图片且模式为桥接时，逐张描述。描述以 `vision_notes` 存入消息，`index` 指向图片在附件中的位置。之后发送历史时，图片由描述文字替代，同时被忽略的字段不进入请求体（`SIDECAR_KEYS`）。
5. **失败可见。** 描述失败或视觉模型不可用时，图片位置写入原因，不静默丢弃。每张图的结果记入 Ledger（`vision.described`），只记录名称、模型、结果与字数，不记录描述内容。
6. **参数按模型可配置（第一版）。** 协议（`anthropic`、`openai_chat`、`openai_responses` 白名单）、图片大小上限（1–8 MiB）、`max_tokens`（1–4096，按协议映射为 `max_output_tokens` 或 `max_tokens`）、超时（5–300 秒）、提示词（不超过 4000 字符，留空使用默认）。超出范围的值会被截断到范围内，协议之外的值会被拒绝。
7. **图片传输格式由协议决定。** 第一版没有单独的传输方式覆盖项：`openai_*` 使用 data URL 图片，`anthropic` 使用 base64 图片块。

## 补充：工具返回的图片

截图类工具（`screenshot`、浏览器截图）会把图片文件随工具结果交给对话模型。只支持文本的模型收到这类图片同样会被网关拒绝，使整次请求失败。因此桥接的范围包括工具返回的图片：

- 工具结果产生时，若处于桥接模式，就像处理用户附件一样由视觉模型逐张描述，描述以 `vision_notes` 存在这条工具消息上；之后每次请求发送的都是同一段文字，图片只描述一次。
- 对话模型不能读图而桥接不可用时，图片位置写明原因。
- 对话模型不能读图时，图片本身永远不发给它；没有描述的旧截图（例如中途换了模型）写明“未发送”。
- 对话模型自己能读图（原生模式）时行为不变：最新的两张截图作为图片消息发送。

## 补充二：自动识别模型能否读图，并提供设置界面

原先“能否读图”只靠手动标记 `vision_support`，默认视为不支持，而桌面端又没有任何界面可以设置视觉模型或做标记，所以文本模型收到图片时没有任何保护，请求被网关拒绝。改为按下面的次序判断，前面的来源胜过后面的：

1. **用户的标记**（设置 ▸ 模型 ▸ 图片，每个模型可选“自动 / 能读图 / 不能读图”）。选“自动”会同时清除下面第 2 项学到的结果。
2. **请求结果**（`vision_learned`）：见下文“观察”。
3. **提供方声明**（`vision_declared`）：取回模型列表时，按各家的写法读取输入类型（Anthropic 的 `capabilities.image_input`，OpenRouter 的 `architecture.input_modalities`，网关常见的 `input_modalities`、`modalities`、`supports_vision`、`capabilities.vision`），存在就记下。
4. **模型名称**：只对明确的家族给出判断（如 claude、gemini、gpt-4o、gpt-5、各种 `-vl`/`vision` 为能读图；deepseek-、gpt-3.5 为不能），像 “Max” 这样的别名不给判断。
5. 以上都没有则为**未知**。

**处理**：能读图的模型按原样收到图片；不能读图的模型，设置了视觉模型就由它描述，没有就在图片位置写明原因，图片本身不发；未知的模型，设置了视觉模型就由它描述，否则按原样发送图片并观察。

**观察**：对未知模型，带图片的请求失败时（明确拒绝：400、404、415、422；或服务端和网关错误：500、502、503、504），用文字说明代替图片再发一次。重试被接受才说明原因在图片；明确拒绝时记住该模型不能读图，网关或服务端错误只对本次会话生效，因为它们可能另有原因。带图片的请求被接受，则记住该模型能读图。登录失败、限流、请求过大、流中断都不当作图片被拒。两种情况都会在对话里留下一条说明，并指向设置页。

**其他**：工具返回的图片（截图）与用户附件走同一套判断；切换模型时图片处理跟随新模型（此前切换模型不会更新，先用视觉模型、再换成文本模型时，对话里已有的图片会原样发给文本模型）；对话里已有的、没有描述的图片，发给不能读图的模型时同样替换为说明。

## 不做（本版本）

- 桌面端设置界面与 IPC 命令尚未接入。后端的 `set_vision_settings` 已就绪。
- 单独的图片传输方式覆盖项（见第 7 条）。
- 按模型名自动预置 `vision_support`。

## 影响

- 只支持文本的模型收到图片时，不再直接转发图片，而是由视觉模型描述。
- 被描述过的图片在后续轮次中以文字形式发送，降低上下文成本。
- 每张图增加一次视觉模型请求，带来额外的费用与延迟。
- 视觉模型的出口与代理行为与对话模型一致，没有绕过现有门禁。

## 验证

- `vision.rs` 单元测试：协议对应的图片格式、大小上限、参数范围、附件替换、响应解析。
- `runtime/vision_turn.rs` 测试：原生模式不加备注；不可用原因写入图片位置；描述失败时备注可见，图片不丢失。
- `delta-core` 全量测试与 `cargo clippy -D warnings` 通过。
