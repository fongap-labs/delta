# ADR-0062：桌面输入控制的同意机制（电脑能力第三步）

状态：**提议**（2026-10-15）。待所有者接受；接受前不引入鼠标与键盘注入。

## 背景

ADR-0059 把鼠标与键盘控制列为第三步，并规定在所有者接受同意机制设计之前不予引入。本文给出该设计。

所有者已于 2026-10-15 确认以下决定：

- 视觉桥暂不实现。驱动模型必须能读取截图（见下文"驱动模型"）。
- 审批采用分级方案：按程序授权，敏感动作逐次确认。
- 拒绝列表包含命令行、脚本宿主、注册表编辑器与安全中心（见第 3 节）。
- 银行与支付客户端、密码管理器：逐次确认，且模型不读取其屏幕内容（见第 3 节）。
- 授权不跨重启保存。

本文按 ADR-0059 第三步列出的要求逐项落实，并把分级方案写成可执行的规则。

## 决定

### 1. 范围

- 第一版只支持 Windows。其他系统返回"尚不支持"。
- 动作分三类：UI Automation 具名控件操作（调用、设置文本、选择）、键盘（文本输入与快捷键）、滚动。
- 坐标点击只作兜底，每次都需确认（见第 3 节）。
- 不做：输入密码或支付信息；以管理员身份提权操作；控制 Delta 自身窗口。

### 2. 总开关、提示与紧急停止

- 设置中的"允许 Delta 操作这台电脑"默认关闭。开启时需确认一次，并说明风险。
- 任务运行期间，屏幕上持续显示顶置提示"Delta 正在控制这台电脑"，附"停止"按钮。
- Esc 为全局紧急停止：立即结束动作循环，释放仍按下的鼠标键与键盘键，并把停止原因写入对话记录。停止后任务结束，需用户重新发起。

### 3. 程序授权（分级）

| 类别 | 处理 |
|---|---|
| 拒绝，不可授权 | 系统设置、命令行与脚本宿主（cmd、PowerShell、终端）、注册表编辑器、Windows 安全中心。由 Rust 运行时内置列表，按进程名与可执行文件路径匹配，随版本维护。 |
| 逐次确认，内容不读取 | 银行与支付客户端、密码管理器。模型不读取这些窗口的屏幕内容，只执行用户明确要求并在审批卡片中确认过的单个动作。详见下文"银行与密码管理器"。 |
| 按程序授权 | 每个程序（进程与发行者签名）首次被操作时弹出审批，说明程序名、窗口标题与计划的动作类别。通过后，本会话内该程序中的普通动作自动执行。 |
| 逐次确认 | 即使程序已授权，下列动作每次都确认：发送、提交或发布消息与表单；删除、覆盖、清空；购买、付款、转账、确认订单；坐标点击。 |
| 永不执行 | 向密码类字段（UI Automation 的 IsPassword）输入；由模型代为输入密码或支付信息。沿用 ADR-0059 的要求：请用户自己输入。 |

规则细则：

- 敏感判断由运行时依据控件名称、控件类型与按钮文字完成，不依赖模型的自我声明。模型可以额外声明，但只能让判断更严格，不能放宽。
- 授权仅限当前会话。用户可在设置中随时撤销某个程序的授权；会话结束全部失效；不跨重启保存。
- 切换到未授权的程序时，动作暂停，并重新弹出审批。

**银行与密码管理器**

- 不能做到"读取内容但不泄露"。读取即意味着屏幕内容（解密后的）会发给模型提供方；加密只保护存储，不保护屏幕显示。因此这类程序中模型不读取屏幕。
- 只要前台或任一显示器上出现这类程序，截屏功能即拒绝，不截图、不发送、不保存。
- 模型不读取这些窗口的文字，包括金额、收款人、账号与密码字段。
- 每个动作仍需用户在审批卡片中确认。卡片只显示模型要操作的控件名称，不显示其他读取到的文字。
- 若完成任务必须从屏幕读取信息，Delta 说明原因并停止，请用户自己完成。

**接管（登录与付款）**

- 遇到登录、验证码、支付或其他敏感输入时，Delta 暂停，并提示用户在程序窗口中自己操作。
- 用户在程序中完成后，点击"继续"，Delta 再恢复动作循环。
- 接管期间，Delta 不截图、不输入、不点击。
- 参考 ChatGPT agent 的接管模式：敏感信息由用户直接输入，不经过 agent。

### 4. 记录与披露

- 每个动作前后各保存一张截图到 `.delta/screens/<run>/`，7 天后删除，沿用 ADR-0059。
- 逐次确认类程序的动作不保存截图（见上文）。
- 审批卡片说明：程序、窗口标题、动作、目标控件，以及屏幕内容会发送给模型提供方。出境范围仍受 ADR-0057 的工作区档位约束。

### 5. 驱动模型

- 动作循环需要模型读取截图。运行时在第一步之前检查所选模型是否支持图片，若明确不支持，或提供方拒绝图片，则终止循环并说明原因。
- 本文不引入视觉桥。在没有原生视觉模型可用时，第三步不可用，这是有意的结果。

### 6. 限制

- 每次运行最多 50 个动作。
- 单个动作超时 10 秒。
- 同一动作连续失败 3 次即停止并报告。
- 目标窗口是提权进程，或受 UIPI 限制时，报告失败，不尝试提权。

### 7. 实现位置与权威

- 注入与 UI Automation 调用位于 `crates/delta-computer` 的新模块（如 `input`）。
- 策略判断（程序列表、敏感规则、授权状态、动作限制）位于 Rust 运行时。模型与界面都不能绕过它。
- 界面只显示提示与授权操作，不做安全判断。

### 8. 验证

- 策略逻辑（列表匹配、敏感规则、授权生命周期、动作计数）用假输入后端在 Linux 上测试。
- 注入本身只能在 Windows 上验证。接受本 ADR 后，需在 Windows 上按以下清单手动测试：总开关、提示、Esc 停止、首次授权、拒绝列表、敏感动作确认、坐标点击确认、截图留存。

## 后果

- 本文取代 ADR-0059 第三步的设计部分。第一、二步的"每次都询问"规则不变。
- ADR-0059 第三步的默认是"每个动作都需审批"。本文以程序授权放宽，这正是 ADR-0059 允许的"明确、可撤销的授权"。
- 银行与密码管理器改为逐次确认，但模型不读取其屏幕内容。这比 ADR-0059 原先设想的"一律拒绝"更具体，也比 ChatGPT agent 与 Claude 的做法（它们允许 AI 在已登录的会话中操作）更保守，代价是这类程序里的功能很弱。
- 第三步依赖原生视觉模型。视觉桥暂不做，因此第三步在没有这类模型时不可用。

## 未决事项

- 无。所有者已于 2026-10-15 确认上述决定。接受本 ADR 的状态变更仍待所有者确认。
