# ADR-0055：报告中的每个数字都可追溯到计算结果

状态：**已接受**（所有者，2026-10-11）。依赖 [ADR-0054](0054-statistics-engine.md)。

**部分实现**：绑定的语法解析与按格式渲染（`numeric_trace` 模块）已实现；2026-10-25 增加了结果产出物的写出（`statistics_record`）、Markdown 报告的渲染与核对（`report_render`、`report_check`，见文末"实现记录"）。绑定清单、`numeric_trace` 校验规则与 `forbid_unbound_numbers` 尚未实现（见 CHANGELOG）。

## 背景

蓝图要求统计输出可追溯（`DELTA_BLUEPRINT.md` 第 4.4 节："统计前提和输出可追踪"）。对于研究分析，尤其是制剂 / CMC 领域，最具破坏性的失败，是报告中出现一个看似合理、但没有任何计算产生过的数字：货架期、置信限、f2 值、模型系数。

现存情况（已核对，并非假设）：

1. **校验规则。** `projects/delta/crates/delta-core/src/validation.rs` 针对工具的产出物评估标准：
   - 产出物数量；
   - 完整性；
   - 必需路径；
   - 大小门槛；
   - 必需子串；
   - CSV 表头；
   - 有效引用的数量。

   `required_substrings` 直接读取文件的原始字节，因此它对 Markdown、CSV 等文本格式有意义，而对 DOCX（一个 ZIP 容器）则没有意义。
2. **标准的来源。** `RuntimeHost::validate_tool_artifacts`（`projects/delta/runtime/tool_execution.rs`）使用工具结果提供的校验标准（`validation_criteria`）进行校验，若未提供，则使用默认值（`min_artifacts: 0`、`max_artifacts: 50`、`require_complete: true`）。能力宿主的结果目前总是传入 `validation_criteria: None`（`capability/host.rs`）。
3. **产出物登记。** 产出物按运行登记，包含路径、类型、大小与 SHA-256（`artifact.rs`，`ArtifactRegistryWriter`）。`ArtifactReader::list_for_run` 列出某次运行的产出物。
4. **没有任何机制把报告中的数字与产生它的计算联系起来。**

从自由文本中提取所有数字并猜测其来源，是不确定的：舍入、单位、百分比、日期与章节号都会被当成数字。该检查必须建立在显式的绑定之上，而不能依赖推断。

## 方案

**A. 自由文本匹配。** 从报告中提取所有数字，并要求每个数字都出现在该次运行的某个结果产出物中。
- 优点：无需改变报告的编写方式。
- 缺点：属于启发式；存在误报（日期、章节号）与漏报（经过舍入或重新格式化的数值）；判定无法被精确解释。

**B. 绑定数字（推荐）。** 计算型能力写出结构化的**结果产出物**。报告通过**绑定**引用其中的数值，由渲染器解析。新增的校验规则检查这些绑定。
- 优点：确定性强；每个数字都有确切的来源（结果产出物、SHA-256、键）；舍入是显式的；信任条可以展示它。
- 缺点：报告必须通过理解绑定的渲染器生成；在规则 3 禁止未绑定数字的前提下，在渲染器之外撰写的叙述不受覆盖。

**C. 模型自我声明。** 由模型列出它使用的数字及其来源。
- 缺点：模型对自己进行报告，并非确定性事实（蓝图第 4.4 节）。予以否决。

## 决定：B

1. **结果产出物。** 计算型能力（例如 ADR-0054 中的 `statistics.*`）写出一个 JSON 结果产出物，其中包含：
   - `values`：具名数值，每个都有 `value`、`unit`（可选）与 `kind`（`estimate`、`ci_lower`、`p_value` 等）；
   - `provenance`：引擎与软件包版本、脚本 SHA-256、输入 SHA-256、方法及其参数。

   它与任何其他产出物一样被登记，因此其 SHA-256 记录在 Ledger 中。
2. **绑定。** 报告模板或草稿通过 `{{result:<artifact-path>#<key>|<format>}}` 引用一个数值，例如 `{{result:out/shelf_life.json#shelf_life_months|%.0f}}`。渲染器能力（先支持 Markdown，DOCX 通过 `document.docx.render`）解析每个绑定并生成报告。它还会写出一份**绑定清单**，即与报告一同登记的 JSON 产出物。对于每个绑定，它记录：
   - 结果产出物的路径及其 SHA-256；
   - 键、原始值与格式；
   - 渲染后的文本及其位置（模板章节）。
3. **新的校验规则 `numeric_trace`。** 标准指定一份报告及其绑定清单。只有当以下条件全部成立时，该规则才通过：
   - 清单中的每个绑定都指向同一次运行中登记的结果产出物，且其 SHA-256 与 Ledger 一致；
   - 该键存在于该产出物中；
   - 用声明的格式对原始值进行格式化，结果与渲染文本完全一致。格式为固定的子集（固定小数位 `%.Nf`、有效数字、整数、百分比）。舍入规则为**四舍五入（round half up）**（被舍去的第一位为 5 时，远离零方向进位），并且先取能读回同一双精度数的最短十进制形式再舍入，因此 2.675 在两位小数下渲染为 2.68。不使用二进制浮点的伪影，也不使用银行家舍入。
   - 渲染文本出现在报告的记录位置。对于 DOCX，该规则读取 `word/document.xml` 中的文档文本，而不是比较原始字节。
   - `forbid_unbound_numbers`：报告的文本中，绑定之外不得出现数字，但标准中声明的允许模式（章节号、日期、"25 °C/60% RH"之类的条件）除外。
     - **对每份正式报告默认开启。** 当 Skill 的校验声明其为 `formal: true` 时，该报告即为正式报告。对于正式报告，Skill 不能关闭该规则，只能增加允许模式；每个允许模式都会随判定结果一同显示。
     - 未声明为正式的草稿与探索性笔记不做检查。信任条显示"非正式报告：数字未经检查"，而不是显示通过。
4. **由 Skill 提供的标准。** 生成正式报告的 Skill，在其校验中声明 `numeric_trace` 标准。该规则本身是通用的，不了解任何领域。领域规则集（例如"稳定性报告必须绑定货架期及两个置信限"）位于 Suite 的 Skill 中。
5. **界面。** 产出物信任条已经显示校验结论与所读取的来源（#132、#139）。对于报告，它增加"N 个数字绑定到 M 个结果"。逐个数字的详情（数值、结果文件、键、SHA-256）按需显示。

## 后果

- `validation.rs` 增加 `numeric_trace` 规则，并支持 DOCX 文本提取。这是 Work 权威中的 Rust 代码；解析器必须像其他不可信文件读取一样有界（限制大小与条目数）。
- 能力宿主必须能够从 Skill 或能力结果传入 `validation_criteria`。目前它总是传入 `None`；这是一项需要记录在 `runtime-public-contract.md` 中的合同变更。
- 所需测试：
  - 绑定到另一次运行的结果产出物，应当失败；
  - 结果产出物被篡改（SHA-256 不匹配），应当失败；
  - 缺少键，应当失败；
  - 渲染文本与格式化后的数值不一致，应当失败；
  - 禁止区域中出现未绑定数字，应当失败；允许模式中的数字，应当通过；
  - DOCX 与 Markdown 报告均需检查；
  - 超大或格式错误的 DOCX，应当失败关闭。
- 无需迁移：现有产出物与校验不受影响。

## 所有者的答复（2026-10-11）

1. 接受 B。
2. 禁止未绑定的数字，是正式报告的默认规则。
3. 舍入采用四舍五入（决定第 3 点）。

## 未验证事项

- DOCX 文本位置规则假设报告由 Delta 模板渲染生成。渲染之后由用户手工编辑的 DOCX 文件不在本检查范围内；此后的编辑会改变 SHA-256，届时校验将不再适用于被编辑的文件。

## 实现记录（2026-10-25）：结果产出物

决定第 1 点（计算型能力写出结构化结果产出物）已由 `statistics_record` 实现：

- 对 `ttest`、`anova`、`chisq`、`correlation`、`regression`，由 R **重新计算**同一份结果，并把其中每一个有限数字写入工作区里的一个 JSON 文件（经审批；副作用 `local_write`；按产出物登记，记录路径与 SHA-256）。数字不来自模型。
- 文件结构：`{"format": "delta.result", "version": 1, "method", "values": {键: {"value": 数字}}, "warnings", "provenance"}`。`provenance` 是该方法本来就返回的来源证明（R 版本、程序与输入文件的 SHA-256、方法、参数）。
- 键是数字在方法结果中的路径，用点连接：`p_value`、`conf_low`、`groups.1.mean`、`coefficients.2.estimate`（数组从 1 编号）。同一个方法每次给出同样的键。
- 研究记录的轮次（ADR-0056）可以用文件路径、SHA-256 和键指向这些数字，`study_evaluate` 会核对它们。

**未实现 / 未验证**

- 这一步没有 `kind`（`estimate`、`ci_lower` 等）和 `unit` 字段；键名本身表达含义。
- `statistics_describe` 与 `statistics_doe` 不写结果文件。
- 在本次开发环境的 R 4.3.3 上，通过能力宿主调用会因 R 版本锁定而拒绝，所以文件的生成逻辑是绕过版本锁定直接测试的；锁定本身另有测试。

### 绑定、渲染与核对（同日）

决定第 2、3 点以 Markdown 先行实现，见 `numeric_trace::report` 与两个工具：

- **`report_render`**（经审批，副作用 `local_write`）：读取 Markdown 模板，把每个 `{{result:<文件>#<键>|<格式>}}` 换成该结果文件中该键的数字，格式为 `%.Nf` 或 `integer`，四舍五入（取最短十进制形式后再舍入，2.675 → 2.68）。写出报告，以及旁边的**绑定清单** `<报告>.bindings.json`：每个绑定的结果文件、该文件的 SHA-256、键、原始值、格式、渲染文本、在报告中的位置（字符偏移）和所在小节。任何一个绑定解析不了（文件不存在、不是 JSON、没有该键、格式未知、没有闭合），整个报告都不写，并一次列出全部问题。
- **`report_check`**（只读）：用清单对照报告和结果文件当前的样子。逐个绑定检查：结果文件的 SHA-256 未变；键仍在且数值等于清单里的原始值；原始值按声明格式舍入后等于渲染文本；报告里该位置确实是这段文本；绑定之间不重叠。**正式报告**（默认）还不得含有绑定之外的数字，除非它们在标题或编号列表的编号里，或被调用者给出的 `allow` 正则覆盖（日期、25 °C / 60 % RH、章节引用等必须由调用方列出）。非正式报告不扫描，并在结果里写明"数字未经检查"。
- 正则有数量（20 个）、长度（200 字符）和编译大小限制；不合法的正则是一条问题，不会 panic。偏移按字符计，中文正文前后的位置不受影响。

**未实现 / 未验证**

- **没有接入产出物校验流程。** ADR 决定的是 `validation.rs` 里的 `numeric_trace` 规则，由 Skill 的 `validation_criteria` 触发；能力宿主目前总是传 `validation_criteria: None`，接入需要改合同（`runtime-public-contract.md`）。现在核对只通过 `report_check` 工具进行，由模型调用并转述；信任条也还没有显示"N 个数字绑定到 M 个结果"。
- 只支持 Markdown；DOCX（`document.docx.render`）没做。
- 结果文件的 SHA-256 是用文件现在的内容核对的，没有和账本里登记的值再比一次。
- 正式报告的"不得含有其他数字"是严格的：任何阿拉伯数字（包括单位里的、型号里的）都算，需要调用方用 `allow` 列出；没有内置日期或单位的例外。
- 一份报告被用户手工编辑后，清单里的位置与散列不再对得上，核对会报告出来（这是预期的）。
