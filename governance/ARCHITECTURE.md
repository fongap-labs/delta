# Delta 应用架构

## 1. 产品定位

Delta 是本地优先、开箱即用、可渐进演进的 AI 工作应用。采用“小内核、大框架、模块化单体”原则：先交付稳定可用的产品，再依据真实需求调整内部结构。

用户应能够在安装或解压后，配置自定义模型 API 并使用主要工作能力；架构升级不得无故提高使用门槛、破坏用户数据或导致插件不可预测地失效。

本文定义目标架构与设计约束，不代表所有目标模块已经落地。当前基座为 Electron / Node.js 与 DeepSeek Harness；Rust 主要用于现有便携启动器，不预设必须迁移到 Tauri 或完整 Rust Runtime。

## 2. 小内核

Delta 自有内核只负责必须由产品长期掌握的控制职责：

- 应用生命周期及必要的模块装配规则。
- 产品配置、用户数据归属、备份与迁移规则。
- 凭据管理、权限决策和隐私策略。
- 核心兼容版本、状态恢复及必要的失败处理。

内核不负责 Agent Loop、MCP、模型提供商实现、办公工具、插件业务、页面组件或完整工作流引擎。不能为尚未存在的职责预建空接口、空包或独立进程。

## 3. 大框架

框架包含 Agent、模型调用、会话、工作区、Tools、MCP、Skills、成果交付等能力。目前优先复用 Harness/Cordis 及其成熟模块；Delta 特有功能集中维护，避免散落到上游代码。

框架是可组合的功能模块集合，不等同于第二套插件协议或插件市场。第一方插件沿用 Harness/Cordis 的真实装载协议。未来仅在现有实现成为可量化的维护、安全、功能或性能瓶颈时，才逐步替换相应模块。

## 4. 安全与数据

- 产品默认本地优先，非用户明确触发不得上传会话或工作数据；保留用户主动的 ZIP、Markdown 导出。
- 第一方遥测、行为追踪、非必要的崩溃上报和上传逻辑应从 Delta 发行实现中删除，而非仅隐藏入口；通过依赖、静态及运行时网络检查验收。
- 用户数据目录、凭据访问、备份与迁移策略由 Delta 定义；暂时使用 Harness 会话格式可以接受，但必须保留可靠的迁移/导出路径。
- 插件共享工具中的路径检查或脱敏不等于沙箱。第三方代码的文件和网络权限，必须依据真实的宿主进程与操作系统安全机制判断，不能仅以“内核控制”为由宣称已经隔离。

## 5. 用户体验与演进

桌面 UI 统一展示 Delta 品牌，产品仅维护中文和英文。模型配置只向用户提供自定义 API 入口；移除不需要的第一方内置提供商装配及代码时，应保留必要的运行时兼容契约。

优先采用单仓库、模块化单体；只有在真实的安全边界、部署边界或独立版本需求出现后才拆分进程/仓库。任何替换必须先通过数据兼容、插件装载和产品回归验证，再移除旧实现；不得无期限并行维护两套主运行时。

目录及模块归属见 [仓库规范](REPOSITORY.md)，工程执行以 [治理入口](GOVERNANCE.md) 为准。
